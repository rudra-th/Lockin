# Android

The Android surface is a **Capacitor 8 shell around `app/`**, not a second UI.
The web app remains the source of truth for tasks, schedules and sessions; the
shell adds the capabilities a browser cannot have.

> Status: the Capacitor shell builds a debug APK, and the `LockinNative` bridge
> covers exact alarms, full-screen alarm screens with Start/Skip, notification
> permission, usage access, per-app screen time, optional app blocking through a
> user-enabled accessibility service, per-app daily limits, an optional
> device-owner kiosk, and optional Google sign-in for cloud sync. Device testing
> is the remaining gate before sharing a release APK.
> Lockin distributes directly — no Play Store. The UI still states the web limit
> plainly: the browser build rings only while Lockin is open.

## Build

Prerequisites:

- Android Studio with **JDK 21** (the bundled JBR works).
- Android SDK platform 36 and build-tools 35+.
- Node 22+.

```bash
npm install
npm run android:build         # cap sync android + assembleDebug
```

The helper uses `gradlew.bat` on Windows and `./gradlew` elsewhere. A different
Gradle task passes through: `npm run android:build -- assembleRelease`.

If Gradle cannot find the toolchain:

```powershell
$env:JAVA_HOME = 'C:\Program Files\Android\Android Studio\jbr'
$env:ANDROID_HOME = "$env:LOCALAPPDATA\Android\Sdk"
```

APK: `android/app/build/outputs/apk/debug/app-debug.apk`. Launcher and splash
art: `npm run android:icons` (Windows, System.Drawing; no Android Studio).

`android/local.properties` points Gradle at the local SDK and is ignored.
`android/app/src/main/assets/public/` is generated by `cap sync` and is ignored;
run sync after changing anything in `app/`.

## Project shape

```text
android/
  app/src/main/
    AndroidManifest.xml
    java/com/lockin/app/
      MainActivity.java          registers LockinNative
      LockinNativePlugin.java    bridge: alarms, usage, permissions, blocking
      AlarmReceiver.java         notification + full-screen intent + Start/Skip
      AlarmActivity.java         lock-screen alarm screen
      AlarmActions.java          queue for Start/Skip taken while closed
      BlockingStore.java         device-local blocking, limits and kiosk config
      LockinAccessibilityService.java  foreground time, block overlay
      LockinDeviceAdminReceiver.java   optional device owner for the kiosk
      BootReceiver.java          re-seeds alarms after reboot
      AlarmScheduler.java        shared scheduling/cancel helpers
    res/xml/accessibility_service_config.xml
    res/xml/device_admin.xml
    res/                         icons, splash, strings, overlay layout
  variables.gradle               SDK levels and AndroidX versions
  capacitor.settings.gradle
```

`capacitor.config.json` sets `webDir: "app"` and `androidScheme: "https"`.
The service worker is not registered inside the native shell; the shell serves
the bundled files directly.

## The bridge contract

`app/assets/js/native.js` is the only web file that talks to `LockinNative`.
Outside the shell every export is inert, so the same `app/` still runs on the
web and in the extension pack.

- On boot it consumes a notification route (cold start lands on Schedule) and
  clears stale alarms — the foreground engine owns the app while it is open.
- On boot and every resume it drains the `AlarmActions` queue: **Start session**
  or **Skip today** tapped on a notification or the lock-screen alarm applies
  once, even if the app was closed when it was tapped.
- On every background transition it seeds the next **14 days** of `remind` and
  `start` events from `eventsBetween`. A `start` event is skipped when the
  block's **Alarm at start** switch is off; the reminder still fires.
- On returning to the foreground it cancels the native alarm window, so an open
  app never rings twice.
- On boot and on every background transition it also pushes the next **14 days**
  of blocking windows: every schedule occurrence that overlaps the horizon
  (including one already running after midnight) plus a live Study Mode window
  while a session is running or paused. Breaks are not blocked.
- Settings → Android shows live pills for exact alarms, notifications,
  full-screen alarms, usage access and the accessibility service, plus a 7-day
  screen-time card from `UsageStatsManager`. App blocking, per-app limits and
  the kiosk live in the separate **Control** tab; Settings keeps the permissions
  and a pointer to it.

## Native capabilities

### Exact alarms

- `AlarmManager.setExactAndAllowWhileIdle(RTC_WAKEUP, at, pendingIntent)`.
- `SCHEDULE_EXACT_ALARM` is declared; on Android 12+ the user may need to grant
  "Alarms & reminders" in system settings. The plugin exposes
  `canScheduleExactAlarms()` and `openExactAlarmSettings()`.
- If permission is denied, fall back to `setAndAllowWhileIdle` and report
  `exact: false` to the web UI. Never claim an exact ring that is not exact.
- A boot receiver re-seeds the next window of alarms from the stored schedule.
- Start alarms ask for a **full-screen intent** on Android 8+ (`AlarmActivity`):
  the screen turns on, the alarm draws over the keyguard, and **Start session** /
  **Skip today** are one tap. Android 14+ can withhold the permission, so the
  receiver checks `NotificationManager.canUseFullScreenIntent()` at runtime. When
  it is denied, the same alarm posts as a loud heads-up notification — never
  silently. Settings → Android shows the current state and opens the system
  toggle.
- Each alarm payload carries `scheduleId`, `day`, `name`, `start` and `end`. Both
  the notification and `AlarmActivity` write the chosen action to the
  `AlarmActions` mailbox, which `native.js` drains; **Skip today** persists the
  occurrence in `settings.blockSkips`, so the hero and the next alarm agree.
- `AlarmActivity` is not exported, does not appear in recents, and owns no
  schedule state: title, body, notification id and the schedule identity arrive
  in the intent.

### Usage access

- `PACKAGE_USAGE_STATS` is a special access permission. The app opens
  `Settings.ACTION_USAGE_ACCESS_SETTINGS`; the user grants it.
- `UsageStatsManager.queryUsageStats` aggregates foreground time per package.
- Lockin's own package (`com.lockin.app`) is filtered out of every row and every
  daily total, so studying in Lockin never counts as phone screen time. The same
  exclusion is applied in `Store.recordScreenTime` before a snapshot is stored.
- No history database, no page content, no pickups, no unlocks, no keylogging.

### Google sign-in (optional sync)

- `@capacitor-firebase/authentication` opens the native Google sheet; the
  returned ID token goes to the Firebase JS SDK (`signInWithCredential`), which
  owns Firestore. `skipNativeAuth: true` keeps a single auth session.
- `capacitor.config.json` registers `google.com` under
  `plugins.FirebaseAuthentication.providers`. The plugin defaults to an empty
  list, and without the entry the native sheet fails immediately with
  “google.com sign-in provider is not enabled”. `npx cap sync android` copies
  that config into `android/app/src/main/assets/capacitor.config.json`, so a
  config change needs a sync **and** a rebuild.
- `android/app/google-services.json` is required for the Firebase integration
  and is **gitignored** — download it from the Firebase console (project
  `lockin-29758`, Android app `com.lockin.app`, release SHA-1 in
  [`android-release.md`](android-release.md)). The web config in
  `app/assets/js/firebase.js` is public by design; Firestore rules are the lock.
- A **debug** APK normally signs with the local debug keystore, whose SHA-1 is
  not the release one registered in Firebase — Google sign-in would then fail
  with `DEVELOPER_ERROR`. This repository avoids that trap: when
  `android/keystore.properties` is complete, `build.gradle` signs **both** debug
  and release builds with the release keystore, so the certificate Google knows
  is the one that ships. If the properties file is absent, the debug APK falls
  back to the debug keystore; add its SHA-1 in Firebase → Project settings →
  Your apps if you need sign-in on that build.
- Signing out leaves local data untouched; Settings → **Delete cloud data**
  wipes the Firestore mirror and then signs out.

### App blocking (opt-in)

This is a direct-APK feature, not a Play Store one. It is off until the user
turns on the accessibility service in system settings and flips the master
switch in Control → App blocking.

- **What the service sees.** `LockinAccessibilityService` subscribes to exactly
  one event, `TYPE_WINDOW_STATE_CHANGED` — "a window came to the front". The
  service config sets `android:canRetrieveWindowContent="false"`, so Android
  will not hand it node trees, text, page content or keystrokes. It reads the
  foreground package name and nothing else.
- **What it blocks.** Only packages the user picked, only inside a focus window.
  The windows are schedule occurrences plus the live Study Mode session
  (running or paused; a break is free time). A stopwatch has no planned end, so
  it covers four hours from the last push, rounded to a quarter hour; the next
  background transition refreshes it.
- **The overlay.** A `TYPE_ACCESSIBILITY_OVERLAY` window covers the app with the
  block name, a live countdown, a progress bar and one action: **Leave this
  app**, which calls `GLOBAL_ACTION_HOME`. It draws above the app, not above the
  system UI, and it owns no app data.
- **Fail open, always.** No overlay when Lockin itself is in front, when the
  service is off, when the app list is empty, or when no window is active. If
  the config cannot be read, nothing is blocked. Launchers, Settings and the
  default dialer are protected: they are hidden from the picker and re-checked
  on every foreground change, so a stale list cannot lock the user out of
  leaving the overlay, opening the service settings, or calling for help. The
  overlay is a focus aid, not a lock: Android lets the user turn the service off
  at any time, and the Settings card says so plainly.
- **The app picker.** `listLaunchableApps()` queries `MAIN`/`LAUNCHER` through a
  narrow `<queries>` declaration — no `QUERY_ALL_PACKAGES`. It lists only apps
  with a launcher icon, sorted by label, with a search field and per-app
  toggles. Lockin, launchers, Settings and the dialer are excluded.
- **Where the config lives.** `BlockingStore` uses device-local
  `SharedPreferences` (`lockin_blocking`): `enabled`, `packages`, `windows`,
  `limits` and the day-bucketed `usage` counters, plus the kiosk flags. It is
  deliberately not synced — which apps are blocked is a property of this phone,
  not of the account.
- **Honest limitation.** The overlay appears when a window change is delivered.
  A 15-second safety check also re-reads the last foreground activity, so an
  app already open when a focus window starts is covered without waiting for an
  app switch. If the device is dozing, Android may delay both until the next
  wake. This is stated in the docs rather than papered over.

### Per-app daily limits

Each app can carry a daily allowance (15 minutes to 3 hours). The Control tab
shows a live bar and a stepper; the same overlay used for blocking draws a
**Daily limit reached** card once the allowance is spent.

- The service tracks foreground time while it sees an app in front and flushes
  on every app switch, screen-off, the 15-second safety tick and service
  destroy. Time is stored per local day under `usage`, pruned to two days, so
  the counter resets at midnight without a job to miss.
- Limits only count while the accessibility service is on. The card says so
  instead of implying device-wide coverage.
- A spent limit is not a lock: raising the allowance in Control frees the app
  immediately, and the overlay leaves the usual system escape routes alone.

### Kiosk (optional)

The kiosk is the one place Lockin can actually hold the phone, and it is a
separate opt-in in Control — not part of Study Mode. A normal session is a
full-screen room; the kiosk asks Android for lock task with
`LOCK_TASK_FEATURE_NONE` and an allowlist of the user's chosen apps.

- **Device owner is the real kiosk.** Run the one-time command from Control (or
  `docs/android.md`) on a fresh install:
  `adb shell dpm set-device-owner com.lockin.app/.LockinDeviceAdminReceiver`.
  Only then can lock task keep the user out of launchers and Settings. Remove it
  with `adb shell dpm remove-active-admin com.lockin.app/.LockinDeviceAdminReceiver`.
- **Without device owner** Lockin falls back to screen pinning where Android
  offers it, labels the state **Limited kiosk**, and never claims the system
  hatch is closed. The accessibility service still covers every non-allowed app
  with a **Kiosk session** overlay whose one action is **Back to Lockin**.
- **Fail open on a deadline.** The JS engine refreshes the kiosk deadline while a
  session is live; native also schedules a `Handler` release at that deadline.
  A killed app, a dead battery or a cancelled session cannot leave the phone
  stuck. On boot, a stale kiosk flag with no live session is cleared.
- **Never covered:** launchers, Settings, the dialer and Lockin itself. The
  allowlist is a convenience for study material, not a way to lock the user out
  of their phone.

The distraction presets in Control add installed short-video, feed and streaming
apps to the block list in one tap. Android can only see an app, not a path
inside it: it cannot tell YouTube Shorts from a normal video without reading
screen content, which Lockin refuses to do. The extension blocks the `/shorts`
and `/reels` URLs themselves; the Android preset blocks the whole app during
focus and says so.

## Permissions

Declared in `AndroidManifest.xml` as the features land:

| Permission | Why |
|---|---|
| `INTERNET` | Capacitor local server and future opt-in sync |
| `SCHEDULE_EXACT_ALARM` | Ring at the scheduled minute |
| `POST_NOTIFICATIONS` | Alarm and reminder notifications |
| `USE_FULL_SCREEN_INTENT` | Show a start alarm over the lock screen (Android 14+ runtime gate; falls back to heads-up) |
| `RECEIVE_BOOT_COMPLETED` | Re-seed alarms after a reboot |
| `VIBRATE` | Alarm pattern |
| `WAKE_LOCK` | Deliver the alarm receiver on time |
| `PACKAGE_USAGE_STATS` | Per-app screen time (special access); Lockin's own package is excluded |
| Accessibility service (user-enabled) | Read the foreground package so chosen apps can be covered, foreground time counted and limits enforced during a focus window. `canRetrieveWindowContent=false`; no text, content or keystrokes. |
| Device admin receiver (optional) | Inert until the one-time `dpm set-device-owner` command; then the kiosk can use lock task. Protected by `BIND_DEVICE_ADMIN`. |

## Release signing

The release signing setup lives in [`android-release.md`](android-release.md):
a gitignored `android/keystore.properties` feeds `signingConfigs.release`, and
`assembleRelease` fails fast — naming the missing piece — until the keystore
exists. When that file is complete, **debug builds use the same release
certificate**, so the SHA-1 registered with Google sign-in is the one on every
APK you test. Without the file, debug uses the standard debug keystore.

## Play policy notes

- Lockin ships directly, not on Play. If it ever goes to Play, the
  accessibility-based app blocking needs an explicit declaration, in-app
  disclosure and a core-function justification — or it stays out of the store
  build. The service config already limits it to package names, one event type,
  no content retrieval.
- `QUERY_ALL_PACKAGES` is restricted and **not** declared. The app picker uses a
  narrow `MAIN`/`LAUNCHER` `<queries>` entry instead.
- Full-screen intents are restricted on Android 14+; the app checks the
  permission at runtime, offers the system toggle in Settings, and degrades to
  a heads-up notification.
- Exact alarms require a user-facing rationale and the `SCHEDULE_EXACT_ALARM`
  permission; the app must degrade gracefully when denied.
- A privacy policy and Data Safety declaration are mandatory before any store
  listing. Draft from [`privacy.md`](privacy.md) and
  [`permissions.md`](permissions.md).
